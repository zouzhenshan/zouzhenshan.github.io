自动驾驶车辆实验平台控制系统设计

面向多人开发和多算法切换的自动驾驶实验平台控制系统架构设计，包含控制器工厂、统一参数与模型管理、数据处理管道和强实时控制线程模型。

Aug 13, 2026

项目背景

自动驾驶车辆实验平台的控制系统承担车辆状态接收、参考轨迹处理、控制律计算、执行器指令发布和实验数据记录等职责。在教学与科研场景中，平台通常需要支持多人并行开发。不同成员可能分别实现 PID、MPC、状态估计器、车辆模型、参考轨迹处理方法和方向盘后处理策略。若这些功能直接耦合在同一个控制节点内部，算法切换会导致大量重复修改，实验结果也难以保持可复现。

本次控制系统架构设计的目标，是在保持 ROS2 topic 接口稳定的前提下，对控制器内部结构进行模块化重构。系统将车辆模型、状态估计、参考轨迹处理、横纵向控制、输出后处理、参数管理和数据记录划分为相对独立的功能单元，并通过统一接口和工厂机制完成对象创建。这样可以降低算法实现之间的耦合度，为多人协作、多模型切换和多控制算法对比实验提供稳定的软件结构。

基于工厂设计模式的控制器架构

图 1 给出了控制系统的总体架构。系统按照数据在一次控制周期中的流向划分为 ROS 接口层、感知与前处理层、核心控制层、后处理层和工具辅助层。实线表示主数据流或控制流，虚线表示参数、模型辨识结果和辅助信息流。

图 1 中，ROS 接口层负责接收 gps、car_ori 和 local_plan 等外部输入，并向执行端发布 controller 和 prediction 等输出。感知与前处理层由 Estimator 和 ReferenceProcessor 组成，前者将原始定位和姿态消息转换为当前车辆状态，后者将局部规划轨迹转换为控制器可使用的参考序列。核心控制层包含模板化车辆模型、纵向控制器和横向控制器。后处理层负责方向盘平滑、执行器饱和约束和前轮转角到方向盘转角的工程映射。工具辅助层提供参数管理、数据记录和参数辨识接口。

控制器架构采用工厂设计模式。ControllerNode 在初始化阶段读取 launch 参数，并根据类型字符串调用相应工厂。车辆模型由 VehicleModelFactory 创建，估计器由 EstimatorFactory 创建，参考轨迹处理器由 ReferenceProcessorFactory 创建，横纵向控制器由 ControllerFactory 创建，后处理器链由 PostProcessorFactory 创建。节点只依赖抽象基类，不直接构造任何具体算法类。

工厂模式在该系统中解决三个问题。第一，算法类型选择与算法对象构造分离，节点初始化逻辑不会随着新算法增多而持续膨胀。第二，所有实现都通过抽象基类暴露统一接口，控制主循环不需要感知 PID、MPC、EKF 或其他具体实现的内部差异。第三，模块替换可以通过 launch 参数完成，便于开展对比实验和回归验证。

控制器基类的接口保持简洁。初始化阶段注入车辆模型和参数管理服务，运行阶段只接收统一的 PipelineContext 并输出 ControlOutput。由此，控制器不直接读取 ROS 消息，也不直接解析全局配置文件。输入契约、参数契约和算法实现被清晰分离。

统一参数与模型管理服务

实验平台的配置可以分为类型选择和参数取值两类。类型选择用于确定本次运行启用哪些模块，例如车辆模型类型、估计器类型、参考处理器类型、横向控制器类型和纵向控制器类型。参数取值用于描述具体模块的内部参数，例如车辆轴距、转向角约束、PID 增益、MPC 权重、滤波系数和后处理限幅。

系统将两类配置分层管理。launch 文件承担类型选择职责，yaml 文件承担参数描述职责。以横向控制器为例，launch 中的 lateral_controller_type 可以选择 PID 或 MPC，yaml 中则分别保留 lateral_controllers.pid 和 lateral_controllers.mpc 的参数节点。切换控制器时无需删除另一类控制器的参数，调参时也无需修改启动文件。

ParameterManager 作为统一参数管理服务，为所有模块提供一致的参数读取入口。每个模块按照自身命名前缀访问参数节点，工厂负责把同一个参数管理对象注入到模块内部。该设计可以避免参数散落在节点、控制器和工具函数中，也便于实验结束后记录完整配置，支撑结果复现。

车辆模型采用统一管理与依赖注入方式。系统通过 VehicleModelFactory 创建 VehicleModelBase 实例，再将该模型注入估计器和控制器。状态估计器可使用车辆模型进行时延补偿，MPC 可使用同一模型构造预测约束，误差计算也可与模型定义保持一致。车辆模型只有一个来源，可以避免不同模块内部各自硬编码模型方程导致的行为不一致。

模板化编程进一步解决了数值类型复用问题。普通仿真、状态估计和时延补偿通常使用 double 类型，MPC 中的自动微分则需要 CppAD::AD<double> 类型。如果车辆模型只提供普通数值接口，MPC 每切换一次模型都需要重新实现预测方程。这里通过 CRTP 适配器要求派生模型只实现一份 stepImpl<T>，框架自动向上提供 double 与 AD 两套入口。

template <typename Derived>
class TemplatedVehicleModel : public VehicleModelBase {
public:
    State<double> step(const State<double>& s,
                       const Input<double>& u,
                       double dt) const final {
        return static_cast<const Derived*>(this)
            ->template stepImpl<double>(s, u, dt);
    }

    State<CppAD::AD<double>> step(const State<CppAD::AD<double>>& s,
                                  const Input<CppAD::AD<double>>& u,
                                  double dt) const final {
        using AD = CppAD::AD<double>;
        return static_cast<const Derived*>(this)
            ->template stepImpl<AD>(s, u, dt);
    }
};

在教学实验中，学生实现一个运动学单车模型后，PID、MPC、EKF 和时延补偿模块均可复用该模型。后续若引入动力学单车模型，也只需在同一抽象接口下扩展模型实现。系统把模型差异限制在模型类内部，控制器和估计器通过统一接口获得模型能力。

数据预处理与输出后处理接口

控制器输入应当具有统一格式。原始 GPS、车身姿态和局部规划消息到达时间不同，噪声水平不同，坐标语义也不同。若每个控制算法自行完成滤波、最近点搜索、时延补偿和参考轨迹重采样，将产生大量重复代码，并使不同算法的输入条件难以比较。

预处理层提供两个主要接口。EstimatorBase 将传感器消息转换为当前车辆状态，可实现直通估计、低通滤波或 EKF。ReferenceProcessorBase 将局部规划轨迹转换为控制器可直接使用的参考序列，可实现固定预瞄、时间配准、弧长插值和样条重采样。处理完成后，系统将车辆状态、参考序列和误差状态封装为统一的 PipelineContext。

图 2 描述了预处理层的数据组织过程。原始消息先进入状态估计器和参考处理器，车辆模型随后根据状态与参考序列计算误差状态，三类数据最终合并为控制器输入上下文。

控制器输出的前轮转角和加速度仍需经过后处理才能形成执行命令。方向盘存在最大转速限制，执行器存在饱和约束，前轮转角与方向盘转角之间还存在传动比映射。若这些工程约束直接写入 PID 或 MPC 内部，算法代码会承担额外职责，不同控制器之间的执行边界也难以保持一致。

后处理层采用顺序处理链实现。典型顺序是先进行方向盘变化率限制，再进行低通平滑，最后执行饱和约束和物理量映射。

图 3 给出了后处理链的基本结构。方向盘防抖、限幅和映射具有明确先后关系，也具有较强组合性，因此适合用顺序链组织。系统其他主要阶段保持固定顺序，后处理层作为局部可组合结构保留一定扩展空间。

模板化编程边界

多人开发要求软件边界稳定。模板化编程解决车辆模型在不同数值类型下复用的问题，工厂机制解决运行时模块选择的问题，统一上下文解决模块间数据交换的问题。三者共同构成控制系统的扩展边界。

在该边界下，新增算法不需要修改主循环。

编写新车辆模型时，开发者继承 TemplatedVehicleModel，实现模型推进、横纵向解耦状态更新和误差计算。编写新控制器时，开发者继承 ControllerBase，从 PipelineContext 中读取状态、误差和参考序列。编写新滤波器时，开发者继承 EstimatorBase，输出标准 CarState。编写新后处理器时，开发者继承 PostProcessorBase，接收并修改 ControlOutput。

主循环只依赖抽象基类和上下文对象。多人并行开发时，MPC 权重调整、EKF 实现、方向盘平滑策略和车辆模型扩展都落在同一套数据契约之上。该结构能够降低合并冲突，也能使实验对比更加可控。

线程模型设计

控制系统的运行时结构需要同时处理异步通信和周期性控制。GPS、IMU、局部规划和参数事件具有异步到达特征，控制回路则要求稳定周期和确定的执行时序。若将 ROS2 回调与控制计算绑定在同一线程中，任意一个耗时回调都可能造成控制周期抖动。

本文将线程模型划分为 ROS2 异步网络层、状态管理层和强实时控制回路三部分。

图 4 描述了控制系统的线程模型。ROS2 异步网络层负责接收外部消息，状态管理层负责维护最新输入缓存和只读快照，强实时控制回路按固定周期读取快照并完成控制计算。

ROS2 异步网络层由 rclcpp::executors::MultiThreadedExecutor 承担。不同订阅回调被划分到合适的 callback group 中，GPS、姿态和局部规划消息可以并发进入。回调函数只进行轻量处理，包括时间戳校验、消息复制和缓存更新。MPC 求解、样条重采样等耗时计算不在回调线程中执行。

状态管理层负责将异步输入整理为控制线程可读取的快照。基础实现可以使用互斥锁保护输入缓存。控制线程在每个周期开始时短暂加锁，将最新 GPS、姿态、规划和参数版本复制到本地 Snapshot，复制完成后立即释放锁。后续预处理和控制计算均在本地快照上执行，避免长时间占用共享锁。

强实时控制回路由固定周期线程或 ROS2 wall timer 驱动。周期开始时读取快照，随后依次运行预处理、横纵向控制、后处理和命令发布。该线程不等待新的 ROS 消息，也不执行复杂参数解析。当某类消息超时，控制线程依据状态机进入降级策略，例如保持上一周期安全命令、限速停车或输出诊断信息。

并发数据交换原则

并发数据交换的基本原则是缩短共享数据的持锁时间。ROS2 回调线程写入最新消息缓存，控制线程在周期入口读取快照。锁只保护数据交换，不保护算法运行。MPC 求解、样条重采样和 EKF 更新等耗时操作均在本地数据上执行。

图 5 给出了共享缓存与控制快照之间的交换时序。回调线程只负责写入最新消息，控制线程只在周期入口复制输入，算法运行阶段不再访问共享缓存。

当实时性要求进一步提高时，互斥锁方案可以演进为双缓冲或原子 shared_ptr 快照。网络线程构造新的不可变快照，并通过原子指针交换发布。控制线程每个周期只读取当前快照指针，避免阻塞回调线程。教学实验平台可以先采用互斥锁和短拷贝实现，在日志证明锁竞争影响控制周期后，再升级为双缓冲方案。

参数更新也应通过快照机制进入控制线程。运行过程中直接修改控制器内部对象存在风险，尤其是 MPC horizon、约束维度、模型类型等会改变对象结构的参数。增益、限幅和滤波系数可以在周期边界更新。模型类型、控制器类型和后处理链顺序属于结构参数，适合通过节点重新初始化完成切换。

ROS2 通信和 C++ 多线程边界

ROS2 executor 的职责是调度 callback。订阅、timer、service 和参数事件均可成为回调来源。MultiThreadedExecutor 允许多个回调并发执行，但并发执行不能自动保证实时性。若某个 callback 持锁时间过长，或在 callback 中调用耗时算法，其他消息处理仍会受到影响。

控制系统可以将 callback group 分为传感器订阅组、参数服务组和控制 timer 组。传感器订阅组采用可重入策略，使 GPS 与姿态消息能够并发进入。参数服务组采用互斥策略，避免同时处理多个参数更新。控制 timer 单独成组，必要时可配合操作系统线程优先级设置，提高控制周期的调度确定性。线程数量本身不是目标，明确区分不同性质的工作才是线程划分的主要目的。

C++ 多线程实现需要遵守以下约束。

  • 回调线程只写最新消息缓存，不持有控制器对象。
  • 控制线程只在周期入口复制共享数据，算法运行期间只读本地快照。
  • 发布命令只发生在控制线程末尾，避免多个线程同时写控制输出。
  • 参数更新先进入参数缓存，控制线程在周期边界应用轻量参数。
  • 所有跨线程对象都要有明确所有权，优先使用不可变快照和 shared_ptr<const T>。

这些约束可以提升运行时可调试性。当控制周期出现抖动时，可以分别检查 ROS2 executor 是否出现回调堆积、状态快照是否存在延迟、控制求解是否超时。问题被限制在明确的层次内，便于定位和验证。

控制周期流程

控制线程每个周期执行以下步骤。

  1. 读取当前时间。
  2. 从状态管理层复制最新输入快照。
  3. 检查 GPS、姿态和局部规划是否超时。
  4. 调用 PerceptionPipeline 生成 PipelineContext。
  5. 横向和纵向控制器分别计算控制量。
  6. 调用 PostControlPipeline 做平滑、限幅和映射。
  7. 发布控制命令和可选预测轨迹。
  8. 记录本周期耗时、输入时间戳和输出命令。

后续可以补充超时分支、降级策略和诊断输出，使其成为完整的实时控制流程图。

小结

本文设计的控制系统将节点、模型、参数、算法和线程边界分离。ControllerNode 保留 ROS2 接口职责，工厂负责模块创建，参数管理服务负责统一配置读取，车辆模型作为共享依赖注入估计器和控制器，预处理与后处理管道分别承担输入标准化和执行命令约束。

线程模型同样采用分层思想。异步网络层负责消息接收，状态管理层负责快照生成，强实时控制回路只在周期入口读取数据，并在本地完成一次完整控制计算。该设计能够支持多人开发、多算法频繁切换和可复现实验，也为后续引入更复杂的车辆模型、估计器和优化控制器保留扩展空间。
